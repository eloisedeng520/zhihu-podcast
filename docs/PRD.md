# PRD：知乎优质回答播客化产品

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 产品暂定名 | 听见回答 |
| 文档版本 | V1.0 |
| 文档状态 | 初稿 |
| 产品形态 | Web / 移动端音频产品 |
| 核心输入 | 一篇获得授权的知乎优质回答，可选关联问题与评论 |
| 核心输出 | 一期可播放、可追溯的 AI 访谈式播客 |

## 2. 产品概述

“听见回答”将一篇知乎优质回答改编成主持人与嘉宾对谈形式的播客。系统不是简单朗读原文，而是理解回答的论点、结构、案例与适用边界，由 AI 主持人通过提问、复述和追问，让用户在通勤、运动、家务等不便阅读的场景中，更轻松地理解长篇优质内容。

节目以原回答为唯一核心事实来源。主持人可以组织表达，嘉宾内容必须忠实于原回答；评论区仅作为可选的听众提问、反驳或补充素材。播放过程中，用户可以查看当前内容对应的原文段落，区分直接引用、忠实改写和 AI 推断。

### 2.1 一句话价值主张

> 让用户像听一场好访谈一样，听懂一篇值得读的知乎回答。

### 2.2 核心体验原则

1. **先理解，后改编**：先提取文章结构和观点，再生成节目脚本。
2. **忠实而不照读**：语言可以口语化，观点和结论不得被擅自扩展。
3. **可听也可查**：音频中的观点能够回溯到对应原文。
4. **单篇回答优先**：原回答是节目主体，问题背景和评论只服务于理解。
5. **明确 AI 身份**：不得使用户误以为节目由答主本人录制。

## 3. 背景与问题陈述

知乎上存在大量信息密度高、篇幅较长、结构复杂的优质回答。用户虽然有消费知识内容的意愿，但在通勤、驾驶、运动和家务等场景中无法持续阅读；直接使用文字转语音，又会保留书面语、图文引用和复杂长句，收听体验差，难以理解和记忆。

现有“文章转音频”产品大多解决“把文字念出来”，没有解决“如何把一篇文章变成适合听的内容”。如果不重构叙事、补充上下文并拆解论证关系，用户得到的只是低质量朗读，而不是播客体验。

本产品要解决的问题是：**如何在不改变答主原意的前提下，把一篇长回答转化成自然、有节奏、有追问且可信的音频节目。**

## 4. 目标用户

### 4.1 核心用户：知识型音频消费者

- 经常浏览知乎或其他知识内容平台。
- 愿意阅读长内容，但可用于阅读的连续时间有限。
- 已有播客、听书或音频课程习惯。
- 希望快速理解一个问题，而不仅是获得一句摘要。

典型任务：

> 当我在通勤、运动或做家务时，我希望用 8—12 分钟听懂一篇长回答的核心观点和论证过程，从而判断是否需要阅读全文。

### 4.2 次要用户：知乎内容作者

- 希望自己的优质回答触达更多音频用户。
- 希望低成本获得可分享的音频版本。
- 关心改编是否忠实、署名是否清楚、内容是否可控。

### 4.3 次要用户：内容运营人员

- 负责筛选适合播客化的优质回答。
- 需要检查观点拆解、脚本来源和最终音频。
- 需要处理生成失败、内容风险和作者反馈。

## 5. 产品目标

### 5.1 用户目标

1. 用户能够在少于原文预计阅读时长 40% 的时间内理解回答的核心结论、主要论据和适用边界。
2. 至少 90% 的嘉宾观点可以定位到明确的原文段落。
3. 标准节目能够在 8—12 分钟内保持自然、连贯且非机械朗读的收听体验。
4. 用户能够在播放过程中无障碍查看原文来源，并理解内容是直接引用、改写还是推断。

### 5.2 产品目标

1. 建立从知乎回答 API 到结构化脚本、音频和来源映射的完整生成链路。
2. 验证“访谈式改编”是否比直接朗读和纯摘要更能提升完播率与用户满意度。
3. 建立可量化的忠实度、安全性和音频质量标准，为后续规模化生成做准备。
4. 形成可扩展到作者自助制作、个性化长度和互动追问的内容基础设施。

## 6. 非目标

1. **不做完整播客社区**：V1 不建设关注关系、评论社区和创作者社交体系，避免偏离内容转化核心。
2. **不还原整个问题下的多人辩论**：V1 聚焦单篇回答，其他回答不作为嘉宾观点来源。
3. **不克隆答主声音**：除非未来获得单独、明确的声音授权，否则统一使用平台提供的合成声音。
4. **不允许 AI 代替答主自由发表新观点**：原文无法支持的内容必须删除，或明确标注为 AI 推断。
5. **不承诺自动核实文章中所有事实**：系统负责忠实改编和风险提示，不默认对原回答的真实性背书。
6. **不在 V1 支持专业音频工作站能力**：不提供复杂音轨、音乐和逐帧编辑。

## 7. 产品范围与版本规划

### 7.1 MVP：完成可信的单篇回答播客化

- 通过 API 选择或输入一篇回答。
- 获取问题、回答正文、作者信息和必要元数据。
- 识别回答的主题、核心结论、论据、案例和边界。
- 生成主持人与嘉宾双角色访谈脚本。
- 为嘉宾发言建立原文段落映射。
- 生成双角色音频并提供基础播放器。
- 在播放过程中同步展示章节、文字稿和原文来源。
- 明确展示 AI 改编声明。

### 7.2 增强版

- 引入优质评论作为“听众提问”。
- 支持 3 分钟速听、8—12 分钟访谈、15 分钟深聊三种长度。
- 支持用户在播放过程中选择观点并追问。
- 支持作者或运营人员编辑大纲、脚本和发音。
- 支持收藏、稍后听、分享音频卡片和继续阅读原文。

### 7.3 长期能力

- 基于用户兴趣自动生成每日节目单。
- 为作者提供自助播客工作台。
- 支持系列化回答、专栏和专题合集。
- 支持多语言播客化。
- 在单独授权前提下支持作者定制声音。

## 8. 核心用户流程

### 8.1 内容生成流程

1. 用户或运营人员选择一篇知乎回答。
2. 系统通过 API 获取问题、回答正文、作者、评论及元数据。
3. 系统判断内容是否适合播客化，并给出预计节目长度。
4. 系统将回答拆解为核心结论、主题章节、论据、案例和局限。
5. 系统生成节目大纲及主持人问题。
6. 系统生成带来源映射的对话脚本。
7. 系统执行忠实度、内容安全和语音可读性检查。
8. 系统分别合成主持人与嘉宾音轨并合并。
9. 用户进入播放页，边听边查看章节和来源。
10. 用户可以跳转到知乎原回答继续阅读。

### 8.2 异常流程

- 回答过短：提示不适合生成标准节目，可生成 3 分钟速听版。
- 回答过长：按语义章节处理，不因上下文限制直接截断结尾。
- 回答缺少明确观点：提示内容更适合朗读或摘要，不生成虚构访谈。
- API 调用失败：保留任务并支持重试，不能生成空白或不完整节目。
- TTS 部分失败：从失败片段继续合成，避免重新生成整期。
- 来源校验未通过：节目不得进入可发布状态。

## 9. 节目内容规范

### 9.1 标准节目结构

采访稿先用一段完整导语交代事件或话题背景，并明确本期采访主题。事件型内容的背景至少应说明主体或人物、时间或阶段、地点或场景、具体发生的事情、引发关注的原因，以及采访要回答的核心问题；背景较长时可拆成两段主持人开场，但应在前两轮对话内完成。信息不确定时使用“原文提到”“作者描述”等限定语，原文没有提供的时间、地点、身份、因果和结果不得补写，也不能用空泛的“最近发生了一件事”替代事实交代。若原文围绕具体事件、个人经历或持续变化展开，主体按“起因 → 经过 → 结果 → 后续进展 → 反思与影响”组织；原文缺少某一环节时直接跳过，不得补写。若原文是一般性知识回答，则按“背景与主题 → 关键观点及依据 → 案例或对立观点 → 边界与适用条件 → 结论”组织。每章只回答一个核心问题，章节标题应体现所处阶段，避免使用“正文”“讨论一”等空泛标题。

| 环节 | 建议时长 | 内容 |
| --- | ---: | --- |
| 冷开场 | 10—20 秒 | 原回答中最能体现冲突或价值的观点 |
| 背景介绍 | 30—45 秒 | 原问题、答主视角、本期讨论范围 |
| 核心访谈 | 5—8 分钟 | 按主题拆解结论、论据与案例 |
| 边界追问 | 1—2 分钟 | 结论在哪些条件下成立或不成立 |
| 评论追问（可选） | 1—2 分钟 | 有价值的评论及答主已有回应 |
| 总结 | 30—60 秒 | 核心结论、关键依据和未解问题 |

### 9.2 角色规范

**主持人**可以：

- 介绍问题背景和文章结构。
- 对原文进行简短总结。
- 提出澄清、深挖、反问和边界问题。
- 提醒用户某一观点是个人经历、价值判断或事实陈述。
- 串联章节和总结内容。

**主持人不得**：

- 宣称未经原文支持的事实。
- 将个人经历表述为普遍结论。
- 暗示节目由答主本人参与录制。

**嘉宾**可以：

- 直接引用或口语化改写原回答。
- 按照原回答已有逻辑重新组织表达顺序。
- 回答原文能够明确支持的问题。
- 直接回应主持人的问题，使用自然的第一人称或无主语表达；不得以第三人称介绍“作者/答主认为”，也不得说“原文提到”“根据材料”等来源说明。

**嘉宾不得**：

- 使用原回答不存在的新事实、案例或立场。
- 为了制造冲突而夸大原观点。
- 回答原文没有信息支撑的问题。

### 9.3 内容来源类型

每个脚本单元必须标记为以下一种类型：

- `quote`：直接引用原回答。
- `paraphrase`：忠实口语化改写。
- `synthesis`：综合原回答多个段落形成的总结。
- `inference`：根据原回答逻辑进行的有限推断。
- `transition`：主持人的结构性串联语言。
- `comment`：来自评论区的提问或补充。

除 `transition` 外，每个脚本单元必须包含至少一个来源段落 ID。`inference` 必须在界面中明确提示，并默认限制在节目总字数的 5% 以内。

## 10. 用户故事

### 10.1 听众

- 作为没有时间阅读长回答的用户，我希望一键生成访谈式音频，从而在通勤时理解回答。
- 作为关注内容可信度的用户，我希望查看当前声音对应的原文，从而判断改编是否准确。
- 作为只想快速了解内容的用户，我希望查看章节并跳转播放，从而直接收听最感兴趣的部分。
- 作为被节目吸引的用户，我希望跳转到原回答，从而阅读细节并了解作者。
- 作为音频用户，我希望调节播放倍速和进度，从而按自己的习惯收听。
- 作为遇到生成失败的用户，我希望看到明确状态并能够重试，而不是一直等待。

### 10.2 作者

- 作为原回答作者，我希望节目正确展示我的署名和原文链接，从而保留内容归属。
- 作为原回答作者，我希望知道节目是 AI 改编而非本人录制，从而避免用户误解。
- 作为原回答作者，我希望能够反馈错误或申请下架，从而保护我的观点和权益。

### 10.3 运营人员

- 作为内容运营人员，我希望预览观点拆解和脚本来源，从而发现错误改编。
- 作为内容运营人员，我希望修改标题、章节、脚本和发音，从而提升节目质量。
- 作为内容运营人员，我希望看到生成失败和校验未通过的原因，从而快速处理异常。

## 11. 功能需求

### 11.1 P0：必须具备

#### P0-1 回答导入

系统应支持通过回答 ID、授权链接或内容列表选择回答，并通过比赛或正式授权 API 获取内容。

验收标准：

- 给定有效回答 ID，系统能够获取问题标题、回答正文、作者标识和原文链接。
- API 数据缺失时，界面明确指出缺失字段，不进入错误的生成流程。
- 相同回答重复提交时，系统能够复用已有任务或明确询问是否重新生成。

#### P0-2 内容适配性判断

系统应在生成前判断回答是否具有足够的信息量和结构。

验收标准：

- 系统能够识别正文为空、过短、主要由图片组成或没有明确论点的回答。
- 不适合标准访谈的回答不会被强制扩写。
- 用户能够看到“适合生成”“仅适合速听”或“不建议生成”及简短原因。

#### P0-3 观点与结构提取

系统应提取文章主旨、三至五个主题、各主题论据、案例和适用边界。

验收标准：

- 每个主题至少关联一个原文段落。
- 主题之间不得仅为同一观点的重复表达。
- 系统不得遗漏对最终结论有决定性影响的限制条件。

#### P0-4 访谈脚本生成

系统应生成主持人与嘉宾双角色脚本，默认节目长度为 8—12 分钟。

验收标准：

- 脚本包含开场、背景、主体、边界追问和总结。
- 对事件型或经历型内容，脚本按“背景与主题、起因、经过、结果、进展、反思与影响”组织；缺少信息的环节可以省略。
- 开场须简要交代采访事件/话题背景和采访主题，主持人的提问应推动听众按时间、因果和影响理解内容。
- 背景交代应具体到“谁、何时/处于什么阶段、在哪里/什么场景、发生了什么、为何受到关注、这期要追问什么”；缺失信息必须明确说材料未提及。
- 主持人问题与嘉宾回答语义匹配。
- 嘉宾发言必须标记来源和生成类型。
- 脚本不得把 AI 推断伪装为答主原话。
- 嘉宾表达不使用“我亲自经历”等第一人称表述，除非原回答明确包含该经历且节目已说明为 AI 演绎。

#### P0-5 来源与忠实度校验

系统应对脚本逐段验证其是否受到原文支持。

验收标准：

- 至少 90% 的嘉宾脚本文字具有明确来源映射。
- 没有来源的嘉宾段落不能进入最终音频。
- 检测到与原文结论相反、因果关系改变或主体错配时，任务进入“需要修订”状态。
- 每一期节目保存生成时使用的原文版本，防止后续原文修改造成不可追溯。

#### P0-6 语音合成

系统应为主持人与嘉宾使用可区分的合成声音，并生成可连续播放的音频。

验收标准：

- 两个角色声音可明显区分，且音量基本一致。
- 数字、年份、英文缩写和专有名词支持发音修正。
- 合成失败可以定位到具体片段并重试。
- 音频不使用或模仿答主真实声音，除非存在独立授权。

#### P0-7 播放与同步文字稿

系统应提供音频播放、暂停、拖动、倍速和章节跳转功能。

验收标准：

- 播放过程中高亮当前脚本段落。
- 点击脚本段落能够跳转到对应播放位置。
- 点击来源能够查看对应原文上下文及原回答链接。
- 页面持续展示“AI 根据原回答改编，并非答主本人录制”的声明。

#### P0-8 生成状态与失败处理

系统应展示获取、分析、写稿、校验、合成和完成等任务状态。

验收标准：

- 用户离开页面后再次进入，能够恢复任务状态。
- 失败时展示失败阶段和可执行操作。
- 未通过内容或来源校验的节目不能被标记为已完成。

### 11.2 P1：增强体验

#### P1-1 评论区听众提问

- 选取高信息量、强相关或获得答主回复的评论。
- 以“评论区有用户问到”进行呈现，不伪装成现场对话。
- 没有原文或答主回复支持的问题，不由嘉宾身份直接回答。

#### P1-2 多长度版本

- 速听版：约 3 分钟，聚焦结论与关键依据。
- 访谈版：约 8—12 分钟，完整拆解回答。
- 深聊版：约 12—18 分钟，加入案例、边界与评论追问。

#### P1-3 互动追问

- 用户可以选中某一节目段落进行提问。
- 系统优先使用原回答和已授权评论回答。
- 素材不足时明确回答“原内容未提供足够信息”，不得以答主身份补充。

#### P1-4 编辑与预览工作台

- 支持修改节目标题、大纲、角色脚本和发音词典。
- 修改嘉宾脚本时持续显示来源覆盖状态。
- 支持重新合成单个片段，无需重做整期节目。

#### P1-5 收藏、分享与继续阅读

- 收藏和稍后听。
- 生成带标题、作者和节目时长的分享卡片。
- 一键跳转知乎原回答。

### 11.3 P2：未来能力

- 个性化节目单和每日自动更新。
- 作者自助提交、编辑和发布。
- 专栏或多篇回答系列化。
- 多语言改编与语音。
- 经单独授权的作者定制声音。
- RSS 或第三方播客平台分发。

## 12. 信息架构与页面需求

### 12.1 首页/发现页

- 优质回答推荐列表。
- 搜索问题或回答。
- 每张卡片展示标题、作者、赞同数、预计阅读时长和预计节目时长。
- 已生成内容直接显示“立即收听”，未生成内容显示“生成播客”。

### 12.2 生成页

- 原问题与回答摘要。
- 适配性结果。
- 节目模式与长度选择。
- 生成进度：获取内容、理解文章、编写脚本、来源校验、合成音频。
- 失败状态及重试入口。

### 12.3 播放页

- 节目标题、回答作者、AI 改编声明。
- 播放、暂停、进度、倍速和章节。
- 主持人与嘉宾当前角色标识。
- 同步文字稿。
- 当前内容对应的原文来源卡片。
- 跳转原回答。
- P1 阶段加入追问、收藏与分享。

### 12.4 运营工作台

- 待生成、生成中、需要修订、可发布和已下架列表。
- 观点卡片、大纲、脚本和来源覆盖率。
- 发音词典和音频片段重试。
- 内容申诉和下架记录。

## 14. 非功能需求

### 14.1 性能

- 已生成节目的播放页首屏在正常网络下应于 2 秒内展示可交互内容。
- 音频支持分段加载，无需等待整期下载完成。
- 生成过程采用异步任务，用户刷新或重新进入不会丢失状态。

### 14.2 可靠性

- API、模型和 TTS 任务应支持分阶段重试与幂等处理。
- 保存生成输入、模型版本、提示词版本和输出版本。
- 单片段错误不应导致整个节目重新生成。

### 14.3 安全与合规

- 仅处理授权范围内的内容和字段。
- 展示作者署名、原文链接和 AI 改编声明。
- 支持按内容 ID下架并停止继续分发。
- 评论中的个人信息、联系方式和敏感经历进入脚本前需经过风险过滤。
- 不使用答主声纹，不将合成声音描述为答主本人声音。

### 14.4 可访问性

- 完整提供同步文字稿。
- 播放控件支持键盘操作和清晰标签。
- 不只依赖颜色表达角色和来源状态。

## 15. 成功指标

正式目标应在获得基线数据后校准。首版建议使用以下假设值：

### 15.1 前置指标

| 指标 | 成功阈值 | 挑战目标 | 统计口径 |
| --- | ---: | ---: | --- |
| 生成成功率 | ≥ 90% | ≥ 95% | 提交后得到可播放且通过校验的节目 |
| 来源覆盖率 | ≥ 90% | ≥ 95% | 有来源映射的嘉宾脚本字数 / 嘉宾脚本总字数 |
| 首次播放率 | ≥ 60% | ≥ 75% | 进入生成完成页后开始播放的用户占比 |
| 标准节目完播率 | ≥ 45% | ≥ 60% | 收听达到节目时长 80% 的用户占比 |
| 原文跳转率 | ≥ 10% | ≥ 20% | 播放用户中打开原回答的比例 |
| 严重忠实度错误率 | ≤ 3% | ≤ 1% | 人工抽检中出现立场反转或虚构关键事实的节目比例 |

### 15.2 滞后指标

| 指标 | 成功阈值 | 评估周期 |
| --- | ---: | --- |
| 7 日二次收听率 | ≥ 25% | 发布后 4 周滚动观察 |
| 用户满意度 | ≥ 4.2/5 | 每期播放后轻量评分 |
| “比直接朗读更易理解”选择率 | ≥ 70% | 与朗读版进行对照测试 |
| 作者改编满意度 | ≥ 80% | 获得作者反馈的节目样本 |

### 15.3 北极星指标

**每周完成收听的有效节目数**：用户收听达到 80%、且节目忠实度校验通过的节目次数。

该指标同时约束消费价值和内容质量，避免只追求低质量的大规模生成。

## 16. 埋点需求

至少记录：

- `answer_selected`
- `generation_started`
- `generation_stage_completed`
- `generation_failed`
- `episode_ready`
- `play_started`
- `play_progress_25/50/80/100`
- `chapter_selected`
- `source_opened`
- `original_answer_opened`
- `speed_changed`
- `episode_rated`
- `fidelity_issue_reported`
- `episode_removed`

所有生成事件应携带回答 ID、节目 ID、生成模式、模型版本和失败阶段；不得在分析事件中传输不必要的回答全文。

## 17. 风险与应对

| 风险 | 影响 | 应对方式 |
| --- | --- | --- |
| 改写改变答主原意 | 失去信任、引发作者投诉 | 逐段来源映射、二次校验、抽样人工审核、申诉与下架机制 |
| 节目听起来像机械朗读 | 用户缺乏持续收听动力 | 先生成采访大纲、控制单次发言长度、增加澄清和边界问题 |
| AI 为答主补充新观点 | 形成虚假表达 | 限制嘉宾只能使用有来源内容，素材不足时由主持人明确说明 |
| 长回答生成成本高或不稳定 | 等待时间长、成本不可控 | 分章节处理、缓存中间产物、音频分片合成与重试 |
| 评论区出现隐私和攻击内容 | 安全与合规风险 | 评论默认不进入 MVP，增强版加入信息量筛选和安全过滤 |
| 原回答后续修改或删除 | 来源与音频不一致 | 保存授权快照和版本时间，建立更新或下架策略 |
| 用户误以为是答主本人播客 | 侵犯身份表达边界 | 统一合成声、显著 AI 声明、避免模仿作者身份特征 |

## 18. 发布门槛

节目只有同时满足以下条件才可进入“可发布”状态：

- 回答授权与 API 来源有效。
- 内容适配性判断通过。
- 嘉宾脚本来源覆盖率达到 90%。
- 不存在立场反转、关键事实虚构或主体错配。
- AI 推断占比不超过 5%，并具有明确标识。
- 音频合成完整，没有缺段、角色错误或不可理解的发音。
- 页面展示作者、原文链接和 AI 改编声明。

## 19. 阶段性推进建议

### 阶段一：可信生成闭环

完成授权 API、内容解析、观点结构、双人脚本、来源校验、TTS 和同步播放器。以人工精选回答建立高质量样本集，验证忠实度和收听体验。

### 阶段二：提升内容表现

增加评论追问、多长度版本、运营编辑、局部重生成和发音词典。通过 A/B 测试比较访谈式改编、朗读版和摘要版。

### 阶段三：用户参与和规模化

增加互动追问、收藏分享、作者工作台、个性化节目单和系列内容，并根据成本、留存与作者反馈决定商业化路径。

## 20. 开放问题

### 阻塞性问题

1. **[数据/工程]** 授权 API 能提供哪些字段？是否包含结构化段落、图片说明、评论回复关系和原文更新时间？
2. **[业务/法务]** 授权范围是否允许保存内容快照、生成衍生音频及向外部分发？
3. **[产品/内容]** 节目发布前是否要求人工审核，还是达到自动校验门槛即可发布？
4. **[工程]** TTS 服务的单次长度、并发、成本和声音授权范围是什么？

### 非阻塞性问题

1. **[设计]** 播放器是优先展示同步文字稿，还是优先展示文章观点卡片？
2. **[产品]** 默认节目长度采用固定 8—12 分钟，还是依据回答长度动态决定？
3. **[内容]** 节目中的嘉宾应称作“内容嘉宾”“观点嘉宾”，还是使用作者昵称并附 AI 演绎标识？
4. **[数据]** 适合播客化的优质回答应主要依据赞同数、收藏数、内容长度，还是人工推荐？
5. **[商业]** 长期优先发展消费者订阅、作者制作工具，还是作为知乎站内内容消费能力？

## 21. 产品决策摘要

- 产品主体是一篇优质回答，不是整个问题下的多人讨论。
- 节目形式为 AI 主持人采访“回答中的观点”，而不是逐字朗读。
- 原回答约占内容依据的 80% 以上；评论仅在增强版作为追问素材。
- 嘉宾发言必须可追溯，主持人可以组织但不能替答主创造新立场。
- MVP 的核心差异化不是声音数量，而是自然的访谈改编和逐段来源映射。
- 产品是否成功，最终取决于用户是否更容易听懂内容，而不是生成了多少音频。
