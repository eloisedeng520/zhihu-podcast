这么看，以后大模型参数增长也不一定继续全部买 GPU FLOPs，相当一部分参数可以变成“CPU/DRAM 上的大型可寻址记忆”。
然后还有 v4  原本那套 CSA + HCA 混合注意力应该也是重构了，V4 Flash 0731 的时候，它的 compress_ratios 基本是 4, 128, 4, 128, 4, 128 ... ， 也就是 CSA 与 HCA 交替。
也就是之前是 CSA 把若干 Token 压成一个表示，再做稀疏检索，然后HCA 直接做 128 倍压缩，然后在高度压缩后的序列上做 attention。
但是 V4.1 已经完全不是这组配置了，V4.1 的主干基本变成 2, 2, 2 ... 1, 1, 1 ...，其中 ratio=2 的层是两个 Token 池化成一个 KV，ratio=1 的层甚至不进行时间维压缩，最后再靠 sparse top-k 控制真正参与 attention 的 Token。
感觉上应该是 V4.1 选择保存更高分辨率的历史信息，然后从另外两个地方省计算：
跨层共享 KV：通过降低时间维压缩率，提高每份 KV 的信息量，同时降低“每层重复保存、重复搜索历史”的浪费，也就是历史表示保存得更细，但一组层共享同一份长程记忆
分级检索：完整长上下文结构已经变成「128 Token 本地 Sliding Window」，再加上「远程 compressed KV memory」，然后配合「一级 block candidate retrieval」和「二级 position-level top-512 retrieval」，最后才执行 sparse attention
共享候选集，但不共享最终 Top-512
所以整体实现上，V4 的 4× CSA + 128× HCA 交替结构，在 V4.1 中已经变成 1×/2× 高分辨率 KV + 跨层 KV 共享 + 跨层 Index 共享 + 两级候选检索 + top-512 Sparse Attention 的组合。
这里其实官方的图说的三种模式，就很直观可以看到前面说的远程 Main KV 到底重新算多少：

把前面两张图连起来，其实就是 V4.1 的完整长上下文策略，比如把它想象成一个人在一百万 Token 的代码仓库里工作：
第 20 层做一次成本较高的全库搜索：“哪些文件、哪些代码区域大概和当前问题相关？”，先得到 Shared Candidate Pool
第 24 层获得更深的语义理解之后：“我现在对问题理解更深了，在刚才那批候选代码里重新选 512 个位置。”
第 25～27 层没有必要重复搜索，直接沿用第 24 层的搜索结果
到第 28 层再重新评估一次。
也就是 Main KV 不需要层层重新建立，然后 Indexer K  也不需要层层重新建立，最后 Top-512 也不需要层层重新搜索。
所以感觉 DeepSeek V4.1 的思路就是：
需要死记的知识，用大但是便宜的条件存储解决
需要从百万上下文里找东西，用分级索引解决
成本高的 Transformer/MoE 计算留给需要动态推理的部分
这也是为什么快的原因，MoE 负责条件计算，Engram 负责条件记忆，CSA2 负责条件访问长上下文，CED 再把 Prefill 和 Decode 的计算需求拆分，这种情况下自然就更快了：
模型可以拥有 552B backbone + 196B Engram 的巨大容量，长 Prompt Prefill 只需要激活 8B，百万 Token 历史也不用每层维护、每层重新扫描，可以直接共享 KV、共享索引并逐级缩小候选集。
